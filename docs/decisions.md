2026-11-27，用户授权将阶段 1 首次公开推送到 `shayft/concordia`，并在 GitHub 托管的 Linux、macOS、Windows 上执行模拟回归。GitHub 的邮箱隐私保护拒绝了首次推送，公开历史将 Git 邮箱替换为 `concordia@example.invalid`，已逐提交核对文件树。此授权用于发布和验证 Concordia 自身，提案 §6.1 对平台管理的用户项目继续适用。

### 2026-11-28 模型调用、预算与上下文

| 问题 | 选择及理由 |
| --- | --- |
| 凭据读取、CLI 预检或上下文检查失败后如何记账？ | 准备阶段只占可用容量。HTTP 请求交给网络、监督器允许启动目标 CLI 之前，先登记派发。未派发的准备记录在结束或重启时退款。监督器明确报告程序未启动时也退款。可能已发但缺少用量的请求保留预估，避免崩溃或丢包使限额失效。工作流和全局账本用同一预留编号核对。 |
| 应怎样检查多轮上下文？ | 每次 API 请求按实际协议 JSON 的 UTF-8 字节数保守估算，包括角色、历史、工具定义、工具结果及协议要求回传的推理。CLI 检查平台提供的输入、工具表与后续回执。原生 CLI 自己管理的系统提示、历史和内部模型轮次对平台不可见。CLI 预算单位为受控程序调用。 |
| 多大的文本要按需读取？ | 文本超过 4,096 字节或工作流上下文上限的八分之一时，有工具回执能力并获授权的成员收到固定版本引用。API 还需至少两次调用才可利用一次读取结果。其他成员收到全文，超过上限时阻止派发。读文本默认每页 2,048 个 Unicode 码点，由调用者指定偏移及每页长度；这样表情等字符可以完整跨页。 |
