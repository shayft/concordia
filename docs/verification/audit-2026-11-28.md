## 两种派发方式

在 Linux 执行 `pnpm benchmark:delivery`。运行两次相同的六卡“按负责人筛选”任务。每次执行数均为 6，主卡的三条验收条件和四个必需槽位的正文完全相同。

| 指标，单位为模拟秒 | 整卡串行 | 阶段性交付 |
| --- | ---: | ---: |
| 前端开始 | 9 | 2 |
| 总工期 | 26 | 15 |
| 至少一张卡在等依赖的时间 | 22 | 12 |
| 至少一张就绪卡在排队的时间 | 14 | 0 |
| 至少一张卡在等用户验收的时间 | 6 | 5 |

每类时间取并集。多张卡同时等待的同一秒只计一次。不同指标可以重叠。固定的工作时长、每卡一秒的验收延迟和接口发布时间均可从脚本输出复核。个人试用时，在同一任务中另记真实模型、返工、人工审批用时和实际账单，再判断收益。

## 受控负载

Linux 运行 `pnpm exec vitest run --reporter=verbose --silent=false apps/server/test/event-history.test.ts`，1 项通过。临时 WAL 库中创建 100 张任务卡和 10,000 条历史事件。随后对正式任务进度写入、读取看板和获取最新 100 条历史分别采样 40 次。该次运行的中位数和第 95 百分位如下，单位为毫秒。

| 操作 | P50 | P95 |
| --- | ---: | ---: |
| 写入一条任务进度 | 0.94 | 2.75 |
| 读取看板 | 0.40 | 1.08 |
| 读取最新一页历史 | 0.17 | 0.32 |

测试还核对前后分页的边界，以及订阅输出缓冲满时停读、恢复后连续收到全部 105 个事件。以上数据取自本次云端 Linux 文件系统，未设置跨硬件性能阈值。

## 合并前系统矩阵

源码 `cc2ae19` 的 PR 矩阵实跑了冻结锁安装、`pnpm lint`、`pnpm test`、`pnpm build` 和 `pnpm test:browser`。每个系统都用启用原生沙箱的 Chrome 打开本机服务，验证草稿刷新后仍在、重新预览、批准并回读六卡模拟交付。Windows 还额外跑了三遍父进程提前退出的回归。

| 系统 | 假模型和假 CLI | 原生 Chrome 与本机服务 |
| --- | --- | --- |
| Linux | 模拟测试通过，295 通过、4 跳过 | 真实 Linux 测试通过。[作业](https://github.com/shayft/concordia/actions/runs/46146076856/job/140982327002) |
| macOS | 模拟测试通过，296 通过、3 跳过 | 真实 macOS 测试通过。[作业](https://github.com/shayft/concordia/actions/runs/46146076856/job/140982326781) |
| Windows | 模拟测试通过，290 通过、9 跳过 | 真实 Windows 测试通过。[作业](https://github.com/shayft/concordia/actions/runs/46146076856/job/140982327082) |

各系统均缺两份用户登录状态下的 CLI 回显录制。其余跳过项由操作系统条件决定，包括 ACL、链接和 POSIX 假 CLI 场景。云端开发容器单独运行 `pnpm test:browser` 时无法启动启用原生沙箱的 Chrome，该环境标记为**尚未验证**。表中的真实浏览器结果来自 GitHub 托管系统。

其后追加的历史 SHA 选择、临时目录检查和真实入口回归包含在源码 `fb6b3c6` 中。[该源码的独立三平台检查](https://github.com/shayft/concordia/actions/runs/46146309186)

在这次独立检查中，Windows 的 README 端到端用例触发原有的 5 秒默认超时，记录耗时 7.7 秒。该用例涵盖权限检查、服务启动和整套 HTTP 审批流程。后续提交给它单设 30 秒时限，仍须通过原有的状态、版本和零模型调用断言。[Windows 失败记录](https://github.com/shayft/concordia/actions/runs/46146309186/job/140983027792)
